# DESIGN

内容を読み取り、次の操作を迷わず選べる画面にする。
装飾よりも、情報の階層、読みやすさ、操作先の明確さを優先する。

## 適用範囲

- このスキルは見た目と操作性の基準であり、特定製品の画面、業務用語、データ構造、認証方式、技術スタックを定義しない。
- 対象の目的と明示された要件を先に確認する。既存のデザインシステムがある場合はその制約に合わせ、以下の標準値を無条件に上書きしない。
- 新しいデザインをこの基準で作る場合、数値や構成を場当たり的に変えない。変更が必要なら、その理由と変える範囲を示す。
- 参照は同梱の `reference/` で完結する。相対パスはこの `SKILL.md` のあるディレクトリを基準に解決する。

## 読むファイル

最初に基礎仕様とレイアウトを読み、対象の部品と操作を確認する。

| ファイル                                  | 正となる情報                                                       |
| ----------------------------------------- | ------------------------------------------------------------------ |
| [基礎仕様](reference/foundations.md)      | 配色トークン、文字、余白、角丸、アイコン、コントラスト             |
| [レイアウト](reference/layout.md)         | 狭い画面と広い画面の構造、寸法、スクロール領域、safe area          |
| [コンポーネント](reference/components.md) | 部品の構成要素、配置、寸法、色・文字の使い分け                     |
| [操作と検証](reference/interaction.md)    | 状態、開閉、遷移、入力、フィードバック、アクセシビリティ、確認手順 |

基礎仕様で定義した色や文字を部品ごとに再定義しない。コンポーネントの仕様は基礎トークンを参照して組み合わせる。
HTML やスクリーンショットは仕様の適用結果であり、それらがなくても同梱仕様から再現できるようにする。

## 作業の流れ

1. **目的を定める。** 利用者、画面の役割、最初に気付くべき情報、主操作、維持する制約を短く明確にする。不足情報が結果を変える場合だけ質問する。
2. **構造を定める。** 対象の情報と操作を分類し、狭い画面・広い画面の配置を示す。製品に不要な設定、アカウント、統計、検索などをテンプレート都合で追加しない。
3. **仕様から組み立てる。** 基礎トークンを用意し、必要なコンポーネントを選ぶ。対象の用語やデータで構成し、既存の実装環境に落とし込む。デザインのためだけにフレームワークやライブラリを追加しない。
4. **流れで確認する。** 単一画面だけでなく、選択、詳細、戻る、入力、フィードバックまで確認する。見た目だけのモックなら、実処理を行っていないことが分かるようにする。
5. **仕上げる。** 操作性、階層、配色、余白、細部の順で見直す。不要な装飾や重複説明を減らし、変更点・確認結果・未確認の点を簡潔に伝える。

## 避けること

- 全要素を同じ大きさ・太さにする、または小さくして情報を詰め込む。
- 色だけに意味を持たせる、アクセント色をすべての要素に使う。
- 中身に関係のない大きな数字、装飾的なグラデーション、発光、過剰なカード、ガラス効果を足す。
- アイコンの代わりに絵文字やフォントのグリフを混ぜる。
- 狭い画面へ多列構成を押し込み、本文や操作領域を犠牲にする。
- 特定製品の名前、サンプルデータ、固定の URL、ファイル構成を別の製品へ持ち込む。
