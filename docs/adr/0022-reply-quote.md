# ADR 0022: 選択した本文の引用は先頭の blockquote として送り、引用カードで見せる

- Status: Accepted
- Date: 2026-11-04

## Context

PC の会話で、エージェントの返信の一部を引用して返信したい。現状はメッセージ全体のコピーしかできず、どの部分への返信かを示すには手で引用を書く必要がある。主端末はスマホだが、スマホのテキスト選択メニューは差し替えられないため、独自の「返信」を出す入口を作れない。

会話は BFF が pi のセッション JSONL から読んだ `ChatMessage`（`id` / `role` / `text` / `at` / `attachments`）で、送信は `POST /api/panes/:id/input` に文字列と添付名を渡すだけ（[ADR 0013](0013-pi-session-chat.md)、[ADR 0018](0018-pasted-image-attachments.md)）。返信先を持つ構造は入力契約に無く、Herdr の `pane.send_input` も `{ text, keys }` しか取らない。

user 本文は plain text として出し、先頭 5 行でクランプしている（[ADR 0014](0014-markdown-rendering.md)）。コマンドのチップは入力欄の中で完結し、送信文字列は `commands.ts` の表が正（[ADR 0016](0016-composer-command-chips.md)）。

引用は「どのメッセージのどの部分か」をユーザーが示すためのものだが、スレッドや返信先 ID を持たせると BFF と pi の両方に構造を足すことになる。引用の範囲は hwc の画面で選んだ文字列でしかなく、TUI 側にも同じ情報を戻せる形が要る。

## Decision

### 書式

- 引用は選択した生テキスト（`\r\n` を `\n` に正規化し、前後の空行だけ落としたもの）として持ち、保存も生テキストのまま行う
- 送信のときだけ Markdown の blockquote を付ける。行頭は `> `、中身が空白だけの行は `>`、引用と本文の間には空行 1 つ。本文が空なら引用だけを送る
- 組み立てと分解は `src/client/reply.ts` の純関数（`normaliseQuote` / `quoteLines` / `composeReply` / `splitQuote`）に閉じる。判断は `canSend` も含めて DOM 無しでテストする（ADR 0007）
- 送信後の user 本文は、先頭の blockquote と続く本文に分解して描画する。先頭に連続する `>` 行だけが対象で、本文中の `>` と、`>` で始まらない本文は触らない

### 契約を変えない理由

- 送信経路は既存の `POST /api/panes/:id/input` のまま。引用は文字列に畳まれるので、BFF・Herdr・pi のどれにも新しいフィールドが要らない
- 引用は pi の TUI でも `>` の付いた本文として読める。hwc だけが解釈する構造をセッションに持ち込むと、TUI と Web で同じ会話の見え方が変わる
- 入力上限は既存の 16,384 bytes（添付注記込み）にそのまま当たる。超過は 413 → `sendInput` の失敗 → `SEND_FAILED_NOTICE` で、引用専用の事前計算や notice は持たない
- 引用だけでも送れる（`canSend` は引用を内容として数える）。引用は下書きと同じ debounce で `hwc-reply:<paneId>` に保存し、送信成功時に即座に消す

### 表示

- 送信後の引用カードは全端末で出す。ユーザーの吹き出しの中に、本文と区別できる左線付きのブロックとして置き、5 行クランプと「もっとみる」は引用 + 本文の全体に効かせる
- コピーは従来どおり生テキスト（`>` 込み）をコピーする。表示からコピー文字列を作り直さない
- 選択・フローティングの「返信」ボタン・入力欄の引用カードは PC だけに出す。判定は CSS ではなくリスナー側でも行い、`hover: none` か `pointer: coarse` の環境では選択の購読そのものを張らない
- 選択が 1 つのメッセージ本文の中で終わるときだけボタンを出す。複数メッセージにまたがる選択、入力欄・ヘッダ・メタ行の選択では出さない
- ボタンは `.hwc-output-wrap` を基準に絶対配置する。`fixed` は分割セルの `container-type` でセル基準になるため使わない
- 押すと選択を固定したまま引用カードを置き、コマンドチップを外して入力欄の末尾へカーソルを移す。`compact` のチップではチップだけを外し、指示の下書きは残して返信本文として送る（`/compact` には戻さない）
- 入力欄の上の引用カードは最大 5 行でクランプし、スクロールバーを出さない。全文は `title` で見せる。編集はできず、範囲を変えるときは選び直す
- 選択変更・スクロール・リサイズ・ペイン切替でボタンを隠す。ボタン表示中は自動追従を止める。押下時は `pointerdown` / `mousedown` で既定動作を止め、ボタン由来の選択の折りたたみではボタンが消えないようにする

### 誤判定を許容する理由

先頭が `>` の本文は、hwc が作った引用か手書きかを区別できない。区別するには印を足してセッションの本文へ書き込むことになり、TUI 側の見え方を変える。書式が同じなら見え方も同じでよいと判断し、手書きの blockquote も引用カードとして表示する。分解は先頭の連続した `>` 行だけに限るので、本文の途中の `>` は影響を受けない。

## Consequences

- 引用は本文の一部になる。引用カードを編集する手段は無く、範囲を変えるときは選び直す
- ユーザーが先頭に `>` を書いたメッセージは引用カードになる。Markdown として解釈されるのはこの先頭部分だけで、本文全体は plain text のまま
- モバイルでは返信の入口が無い。送信後のカードだけは読める
- 引用の組み立てとフローティングボタンの位置はブラウザの選択 API に依存する。折り返しをまたぐ選択では、ボタンが選択範囲の外接矩形の下に出る
- 分割セルの簡略表示では、引用カードと添付行が縦に積まれる。引用は `order: -1` と `flex-basis: 100%` で入力欄の上に全幅で置き、入力欄を潰さない
- 引用は `REPLY_MAX_LENGTH`（8,000 文字 = 下書きと同じ）を超えると保存しない。メモリ上では使えるので、その場の送信はできる
- 長い引用は入力欄の上では 5 行で切れる。続きは `title` のツールチップで読むことになり、スマホやタッチだけの端末では全文を読めない。引用カード自体は PC 限定なので、そこでの割り切りとする
- 引用の保存は下書きと同じ 250ms の debounce。送信成功時だけ即座に空にし、ペイン切替や再読み込みで古い値が戻るのを避ける

## Alternatives

- **返信先 ID を BFF とセッションに持たせる**: 引用の範囲と対象メッセージを構造として残せるが、Herdr の入力契約（文字列）を超え、TUI 側に表示手段が無い
- **選択範囲を画像にして添付する**: 位置関係は正確だが、モデルが画像を読めるかは hwc が知る情報ではない（ADR 0018）
- **スマホの選択メニューに返信を足す**: OS のメニューを差し替える手段が無い。共有メニュー経由の取り込みは別の話になる
- **user 本文全体を Markdown として描画する**: 手書きの `>` も含めて一貫するが、ユーザーの書いた記号が勝手に整形される（ADR 0014 の範囲を広げる）
- **引用の記号を独自の目印にする**: hwc は区別できるが、TUI で読めない本文になる
