# ADR 0084: 本文の相対パスのリンクを解決して開く

- Status: Accepted
- Date: 2026-11-15
- Revises: [ADR 0014](0014-markdown-rendering.md) の「相対パス・ファイルパスのリンクはリンクにしない」判断
- Revises: 2026-11-17 に拡張子の無いファイルも、開くときに中身を見て配る

## Context

[ADR 0014](0014-markdown-rendering.md) は、相対パスのリンクを `literal`（等幅の原文）として出していた。理由は「hwc の BFF はファイルを配信しないため、押しても 404 になる」だった。

その前提は [ADR 0051](0051-agent-html-preview.md) で崩れている。`GET /api/panes/:id/preview/<根の番号>/<相対パス>` がチェックアウトと追加根の配下を配信し、[ADR 0041](0041-agent-message-images.md) / [ADR 0065](0065-outside-preview-root.md) の `realpath` と配下判定で根の外を落としている。

一方、本文のパスを拾う `messagePathCandidates` は画像と HTML しか受けていなかった。エージェントは `[設計](docs/notes.md)` のようなリンクをよく書くが、押せないうえにチップも出ない。`docs/preview/index.html` をリンクで書いても、押せない原文の下にプレビューのチップが並ぶだけになる。

## Decision

- リンク記法の destination として本文に現れたパスだけをリンクにする。裸のパス・インラインコード・コードフェンスの中は対象外（ADR 0014 のまま文字）。裸のテキストパスは候補にもしない。候補の枠は 20 件で、チップと共有している（[ADR 0041](0041-agent-message-images.md)）ため
- BFF はチップと同じ根（チェックアウト、`/tmp`、`HWC_PREVIEW_ROOTS`）で destination を解決し、実在したものだけを `ChatMessage.links` に載せる。`href` は本文に書かれた表記そのもので、配信 URL ではない。名前・版・根の番号はチップと同じ契約（[ADR 0041](0041-agent-message-images.md)）
- クライアントは `href` が一致したリンクだけを `<a>` にする。一致しなければ今までどおり原文を `literal` で出す
- 開き先はチップと同じにする。`html` はプレビューのタブ、画像は拡大ダイアログ。`text` は `previewUrl` を新しいタブで開く。修飾キー付きのクリックはブラウザの既定動作に任せ、リンク先をそのまま開ける
- 開けるテキストは拡張子の明示リスト（`md` `txt` `csv` `ts` `tsx` `jsx` `js` `mjs` `json` `css` `yaml` `yml` `toml` `sh` `py`）と、拡張子の無いファイル。ドット始まりの名前（`.env` `.secrets.md`）は配らない。ディレクトリがドット始まりでもファイル名が普通なら対象（`.github/workflows/ci.yml`）
- 拡張子の無いファイルは、開くまでテキストかバイナリか分からない。文字として配る経路だけ、先頭 8000 バイトに NUL が無いことを確かめ、バイナリは 415 と短い文言で断る。一覧を出すときは中身を読まない
- テキストは `?raw=1` を付けたプレビューの URL で新しいタブに開き、`text/plain; charset=utf-8` で返す。同じ URL は HTML のアセットとしても使うので、`raw` が無いときは `text/javascript` などの実行可能な型のまま（iframe の中のモジュールを壊さない）
- `previewContentType` にテキストを足す。HTML から読み込まれるスクリプトの案内（[ADR 0067](0067-preview-root-label-and-warning.md)）は、`text/javascript` で配るものだけを「読み込める」と数える
- 版を etag に混ぜる。リンク先の中身が変わったら、304 で古い URL を返さない
- チップは今までどおり `html` と画像だけに出す。同じファイルへの入口がリンクとチップの 2 つになるが、行き先は同じなので許容する

## Consequences

- 本文のリンクから、モック・スクショ・設計メモをその場で開ける。テキストは新しいタブで生の中身（整形なし）
- 配信対象は拡張子の一覧と、拡張子の無いファイルで決まる。一覧に無い拡張子とドット始まりのファイルは、実在しても押せないまま原文で出る
- 拡張子の無いバイナリは、ツリーでは開ける行として出る。開くと 415 の文言になり、ファイル一覧には穴を空けない
- 裸のテキストパスを候補にしないので、本文にパスを並べてもチップの枠は減らない
- テキストを配る経路が増える。根の配下に限る判定はチップと同じだが、`repo` の中の `.md` と、`LICENSE` のような拡張子の無いファイルを LAN の誰でも読める状態になる（[ADR 0010](0010-lan-access.md)）。認証は無いままで、ドット始まりを除くことが境界になる
- `literal` のままのリンクは、原文に戻るのでコピーできる（[ADR 0018](0018-pasted-image-attachments.md) の意図は保つ）
- 同じファイルをリンクとチップの両方で出す。冗長だが、本文の流れの中で押せる利点を取る
- テキストは整形されない。`.md` を読みやすく出したいなら別の仕組みが要る

## Alternatives

- **全ファイルを配る**: `.env` や鍵も LAN から読める。拡張子の一覧と、ドット始まりを外すことで絞る
- **拡張子の無いファイルを一覧の時点で読む**: ツリーを出すたびにディレクトリ内のファイルを開くことになり、件数の上限と読み取りの失敗を扱う必要がある。バイナリかどうかは開いたときだけ確かめる
- **裸のパスもリンクにする**: 本文の見た目を変えずに押せる範囲だけが増えるため、どこが押せるか分からなくなる。リンク記法を書いた箇所だけにする
- **テキストもチップにする**: チップは「見て確認するもの」の場所で、本文中の参照とは役割が違う。`text` はリンクだけで足りる
- **リンクのたびに別ルートを足す**: プレビューの経路が根の番号とパスをそのまま受けるので、型だけ足せば済む
