# ADR 0018: 貼り付けた画像はペイン配下に保存し、本文には注記のパスだけを載せる

- Status: Accepted
- Date: 2026-11-03

## Context

スマホのスクショや PC のクリップボード画像、PC でドラッグした画像ファイルを pi へ渡す経路が無く、一度ファイルへ保存してパスを打つ必要がある。hwc の主利用端末はスマホ（LAN 内の iOS Chrome）で、UI フィードバックを画像で送る用途に合う。

BFF は Herdr / pi と同じユーザー・同じホストで動き、pi のセッション JSONL を絶対パスで読んでいる（[ADR 0013](0013-pi-session-chat.md)）。BFF が保存した画像は pi の `read` で開ける。

保存先の候補と制約:

- ペインの `cwd` 配下: Herdr が返すが、ペインを作り直すと変わり、リポジトリを汚す
- pi のセッションと同じ場所: セッション形式の一部になるため、pi 側の変更に追随が要る
- BFF の状態ディレクトリ: 作業ツリーと無関係で、ペインを作り直しても場所が変わらない

マルチモーダル注入（画像ブロックを API へ直接渡す）はできない。hwc は Herdr の `pane.send_input` に文字列を流すだけで、pi のモデル呼び出しには触れない。pi の `read` は画像を image ブロックで返すが、モデルが `input: ["text","image"]` でないと中身は渡らず、非対応の注記に置き換わる。どのモデルが画像を読めるかは hwc が知る情報ではない。

## Decision

- 画像は `$HWC_STATE_DIR`（既定は `${XDG_STATE_HOME:-~/.local/state}/hwc`）配下の `attachments/<pane-id>/` に保存する。絶対パスでない `HWC_STATE_DIR` は採らず、既定へ落とす。保存先は `createApp` のオプションで受け取り、テストは一時ディレクトリを使う
- キーはペイン id。ペインを作り直すと旧添付は参照されないまま残る。自動削除はしない
- ペイン id はディレクトリ名になるため、`..`・`/`・`\`・制御文字を含む id をパスへ連結する前に弾く。名前も固定書式（`pasted-<YYYYMMDD>-<HHmmss>[-n].(png|jpg|webp)`）を通してから連結する
- 保存名はサーバが決める。`image/jpeg` は `jpg`。同名は上書きせず `-1`、`-2` と連番にする（`wx` で作成し、既存があれば次を試す）。時刻はローカル時刻
- 受け付けるのは png / jpeg / webp の 1 枚 10 MB まで。SVG は同一オリジンでスクリプトが動く形式なので、保存も配信もしない。1 メッセージ 4 枚まで
- 未対応の形式はクライアントで弾いて通知する。paste に画像が入っていたら、受け付けた分だけをアップロードし、未対応の形式があれば「対応していない画像形式です」を入力欄の上に出す（テキストだけの paste は既定動作のまま、アップロードする画像が無ければ既定動作を止めない）。BFF の 415 は同じ文言の防御として残す。UI からは踏めなくなるが、契約としては allowlist を維持する
- `POST /api/panes/:id/attachments` は生バイトを受け、`{ name }` を返す。型の判定は body を読む前（415）。`Content-Length` の事前検査と読み終えた実バイト数の両方で 413
- `GET /api/panes/:id/attachments/:name` はペインの実在と `chat: true` を確認してから名前の書式を検証し、そのペインの保存先配下に解決して返す。`X-Content-Type-Options: nosniff` と `Cache-Control: private, max-age=31536000, immutable` を付け、名前から決めた型で返す
- 画像の受け口はクリップボードの paste と、PC でのファイルのドラッグアンドドロップ。ドロップは composer 全体で受け、`DataTransfer.files` を paste と同じ allowlist・上限・通知に通す。`Files` を持つドロップは画像以外も既定動作へ流さない（ブラウザにファイルを開かせない）。ドラッグ中は composer を面と内側の破線で強調し、落とせる範囲を見せる。シェルペインは paste と同じく受け付けない
- 本文には `<attached_files>` 注記で絶対パスだけを載せる。本文が空なら注記だけ、空でなければ空行 1 つを挟む。マルチモーダル注入はしない
- `POST /api/panes/:id/input` は `attachments` を最大 4 件受け、空 text を許す。ペインと各 name の実在を確認してから注記を組み立て、**注記込み**のバイト数で上限を検査する。5 件以上は 400
- 履歴では BFF が注記を strip し、`ChatMessage.attachments`（ペイン配下のファイル名のみ）を返す。絶対パスはクライアントへ渡さない。strip は最後の 1 組だけを見て、本文末尾の空行も落とす。有効な名前が 1 つも取れない注記は strip しない（書式の外れた注記を消して本文だけを捨てない）。strip 後の本文が空でも添付があればメッセージを残す
- 添付を受け付けるのは `chat: true`（pi の path セッションを持つ）ペインだけ。シェルペインの paste では、画像も、途中に改行を含むテキストも扱わない（シェルは 1 行ずつしか渡せない。末尾の改行だけは落として差し込む）

## Consequences

- 画像はパスの提示までで、モデルが `read` を呼ばない限り届かない。テキスト専用モデルでも送信は成功し、pi が `[Current model does not support images...]` を返す。hwc はモデルの画像対応を知らないので警告を出さない
- BFF と pi が同じユーザーで動くことが前提になる。別ユーザー・別ホストに分けると `read` が開けない
- ペインが作り直されると旧添付は参照されないまま残る。掃除の手段は持たない
- 認証の無い LAN 公開（[ADR 0010](0010-lan-access.md)）では、誰でも 10 MB × 4 を繰り返し書き込める。増えるのは書き込み量と配信バイト列で、露出の種類は変わらない
- 注記は本文の一部なので、ユーザーが同じ形の文字列を自分で書くと strip の対象になり得る。最後の 1 組だけを見るので、本文中の同種の文字列は残る
- チップを外した画像や、送信しなかった画像は保存先に残る。取り消しは持たない
- 上限の大きさと形式の一覧は、案内文も共有定数から組み立てる（`MAX_ATTACHMENT_BYTES` と allowlist）。片方だけを変えて案内だけが古い数値を出す状態を作らない
- 画面上のサムネイルは配信 URL をそのまま `img` に使う。object URL は使わない（送信後も同じ URL で読める）
- 履歴の画像は新しいタブで開く。ライトボックスも Markdown への画像描画もしない

## Alternatives

- **ペインの cwd 配下に保存する**: エージェントがそのまま相対パスで開けるが、ペインの作り直しで場所が変わり、リポジトリの作業ツリーを汚す
- **base64 で JSON に載せて保存する**: 保存形式は 1 つにまとまるが、配信のたびにデコードが要り、メモリ上のサイズが 4/3 に増える。生バイトのまま置けば `read` もブラウザも直接扱える
- **マルチモーダル注入**: モデルの画像対応を hwc が知る必要があり、Herdr の入力契約（文字列）を超える。pi 側の変更が要る
- **自動削除（TTL・件数上限）**: 保存量は抑えられるが、消した添付を履歴が指したままになる。必要になったら別に決める
- **`pick` で添付を選ばせる**: hwc はファイル一覧を持たず、スマホの写真選択は OS の UI に任せた方が速い。paste とドロップで足りる
